## 2. 실사용 발견 문제 — 항목별 상세 (260505)

각 항목은 **상황 → 현재 → 기대 → 수정 결** 4단계로 정리. 마일스톤 워크플로우 진입 시 컨텍스트 손실 방지 목적.

### 서버: 검색·태그 정합 (M1)

#### A1. "모바일 개발" 탭에 무관한 기사 (DEBT-MVP16-01)

- **상황**: 사용자가 피드의 "모바일 개발" 태그 탭을 클릭
- **현재**: Tavily 검색 결과에 포켓몬 카드 / 게임 기사 등 무관 토픽이 섞여 들어옴. 정상 기사도 일부 포함되긴 함 (예: `Vibe coding platform Lovable now available for iPhone`).
- **기대**: 태그와 정합한 기사만 노출
- **수정 결**: `server/src/api/feed.rs::tag_search_keyword()` 키워드 매핑 정밀화. Tavily 호출에 언어/도메인 필터 추가. 또는 후처리 LLM 보정 옵션 검토.

#### A2. 한국어 기사 0건

- **상황**: 어떤 태그를 검색해도 결과에 한국어 기사가 거의 없음
- **현재**: Tavily 쿼리가 영어 일변. KR 도메인/언어 옵션 미적용.
- **기대**: 한국어 기사도 일정 비율 포함
- **수정 결**: Tavily 호출에 한국어 키워드 병행 + KR 도메인/언어 옵션 추가. 또는 KR/EN 두 패스로 분할 후 합치기.

#### A3. 태그 필터 합산·매칭 정합

- **상황**: 전체 피드 N개 기사를 각 태그 필터로 나눠 합치면 N과 안 맞음. "오픈소스" 태그 필터에 IBS 의약품 같은 무관 기사 포함 사례 발견.
- **현재**: 전체 피드 검색과 태그별 검색이 별도 쿼리. 한 기사가 다른 태그 검색 시 매칭 결과가 일관되지 않음. (한 기사가 여러 태그에 속할 수 있어 합산 ≠ 전체는 정상 — 진짜 문제는 **매칭 자체가 잘못된 것**)
- **기대**: 매칭은 정확. 한 기사가 N개 태그에 속하면 그 매칭이 일관됨.
- **수정 결**: 검색 전략 재설계 — (a) 태그별 검색 후 통합·캐시, (b) 전체 검색 + 사후 태그 분류. step-6 진단 후 결정.

### 서버: 텍스트·LLM 출력 (M2)

#### B1. snippet/본문에 raw 마크다운 노출

- **상황**: 피드 카드 snippet 또는 기사 본문 표시 영역
- **현재**: `***title***`, `[text](/path)`, `### 헤더` 같은 raw 마크다운이 그대로 출력됨. 어떤 기사는 다른 기사의 raw markdown까지 snippet에 섞여 들어옴 (예: dongascience 기사의 snippet에 KAIST/Perigee 기사 raw 포함).
- **기대**: 사용자에게는 plain text 또는 정상 렌더링
- **수정 결**: snippet/본문 처리 파이프라인에 sanitize 단계 추가. plain text 변환 / 마크다운 렌더링 일관 정책 결정 (step-1).

#### C1. 한국어 요약에 한자 혼입

- **상황**: 한국어 기사 요약 결과 표시
- **현재**: Groq llama 모델이 한국어 출력에 일부 한자(`查看` 등) 섞음. 프롬프트가 출력 언어 제약 약함.
- **기대**: 한국어 출력에 한자/외국어 혼입 없음
- **수정 결**: 요약 프롬프트에 출력 언어 제약 명시 + 후처리에서 한자 감지 시 재요청 또는 변환. 모델 변경 검토 가능.

#### C3. 직업 미설정 시 인사이트 미노출 (DEBT-MVP16-03)

- **상황**: 사용자가 설정에서 직업을 비워둔 상태로 기사 열기
- **현재**: 인사이트 자체가 노출 안 됨. 직업이 있어야만 인사이트 생성/노출.
- **기대**: 인사이트는 직업 무관 기본 노출. 직업이 있으면 직업 시각이 추가/대체. (요약·인사이트와 재작성은 독립 기능)
- **수정 결**: 인사이트 생성을 직업 의존 분기에서 분리. 기본 인사이트(범용) + 직업별 인사이트(있으면) 구조로.

### 서버: 데이터 모델·재작성 정합 (M3)

#### D1. occupation 삭제 불가 (DEBT-MVP16-02)

- **상황**: 사용자가 설정에서 직업 입력 후, 빈 값으로 다시 저장
- **현재**: 빈 값이 "변경 없음"으로 처리되어 이전 직업 유지. PATCH 핸들러 `Option<String>` 패턴이 null/empty 구분 불가.
- **기대**: 빈 값/null 저장 시 occupation 실제 삭제
- **수정 결**: `Option<Option<String>>` 패턴 또는 명시적 `clear_occupation` 플래그. 서버 PATCH 핸들러 + 클라이언트 페이로드 정합.

#### C2-bug. 직업 바꿔도 본문 안 바뀜

- **상황**: iOS 개발자로 설정 → 어떤 기사 재작성 → 저장 → 설정에서 프론트엔드 개발자로 변경 → 같은 기사 다시 보기
- **현재**: 본문은 iOS 시각 그대로. 헤더 라벨만 "프론트엔드 개발자 시각으로 재작성"으로 바뀜. rewrite 캐시 키가 `(user_id, article_url)` 단일이라 occupation이 키에 없어 같은 본문 반환.
- **기대**: 직업 바꾸면 그 직업 시점의 본문 표시. 없으면 새로 생성. 이전 직업 시점은 DB에 보존(누적).
- **수정 결**: rewrite 캐시 키를 `(user_id, article_url, occupation)` 복합 키로 확장. 조회 시 현재 직업 시점 hit/miss 판정. **다중 시점 UI는 이번 MVP 미포함** (§3, §5).

#### D2. 오답 노트에 원문 URL 미저장

- **상황**: 사용자가 퀴즈 오답을 저장 → 오답노트 탭에서 그 오답 클릭
- **현재**: 원문 기사 이동 불가. wrong_answer 저장 시 source_url이 없음. (피드는 5분 캐시로 휘발성이라 원문 URL을 같이 저장해야 추후 접근 가능)
- **기대**: 오답 클릭 시 원문 기사로 이동 가능
- **수정 결**: wrong_answer 스키마에 `source_url` 컬럼 추가. 저장 API/페이로드 확장. **클릭 시 UI(새 탭 vs 인앱 웹뷰)는 step-1에서 결정**.

### 클라이언트: 표시·회귀 (M4)

#### E1. 앱 피드 카드에 기사 태그 미표시

- **상황**: 앱(iOS) 전체 피드 화면에서 카드 보기
- **현재**: 카드에 태그가 표시 안 됨. 웹은 카드에 태그 표시됨 (웹 ↔ 앱 싱크 불일치). 사용자 메모: "전체 피드에서 태그별로 나눠서 표현하고 있는데" — 카드에 태그가 보여야 분류 인지 가능.
- **기대**: iOS 카드에 태그 라벨/칩 표시 (웹과 일관)
- **수정 결**: 서버 응답에 article.tags 존재 여부 확인 → 누락이면 추가. iOS Feed 카드 뷰에 태그 칩 렌더링 추가.

#### F1. 실기기에서만 오답 저장 안 됨

- **상황**: iOS 시뮬레이터에서 오답 저장 → 정상. 동일 시나리오를 실제 iPhone에서 → 피드 오답보기/즐겨찾기/오답노트 어디에도 안 나타남.
- **현재**: 환경 분기 회귀. 시뮬레이터/실기기 차이가 의심됨 — Keychain 읽기, 인증 토큰 만료, API base URL 분기, 또는 ATS 정책.
- **기대**: 실기기에서도 시뮬레이터와 동일 동작
- **수정 결**: **step-6에서 진단 필수** — 실기기 로그/네트워크 응답 확인, 토큰/Keychain 동작 확인. 원인 확정 후 픽스.

#### F2. 앱 오답노트 태그 필터 미동작

- **상황**: 앱 오답노트 탭에서 태그 필터 칩 클릭. 이전 MVP에서 동작했던 기능.
- **현재**: 필터링 결과가 변하지 않음. 클라이언트 로직 회귀인지 서버 응답 변화인지 불명.
- **기대**: 태그 칩 클릭 시 해당 태그 오답만 노출
- **수정 결**: **step-6에서 진단** — git log/blame으로 마지막 동작 시점 확인 + 현재 코드 흐름 추적. 필터 로직 복원.

## 3. C2-bug 처리 방향 (합의)

**(3) 직업별 누적 저장 — 직업별로 시점이 따로 살아있는 구조**

### 이유

- 사용자 동기("여러 시점")와 정합 (`memory: user_app_motivation`)
- 본인 사용 + Groq 저렴 → 비용 부담 작음
- 데이터 모델 변경 작음: rewrite 키에 `occupation` 컬럼 추가

### 스코프 (이번 MVP에서)

- 캐시 키 변경: `(user_id, article_url) → (user_id, article_url, occupation)`
- 직업 바꿨을 때 시점 hit이면 즉시 표시, miss면 새로 생성
- **다중 시점 UI(시점 칩, 즉석 전환)는 이번 MVP 미포함** — 다음 MVP 후보 (§5)

### 의미 변화

설정의 "직업"은 여전히 단일 (현재 시점). 다른 직업으로 바꿔도 이전 시점은 DB에 남아있음 → 다시 그 직업으로 돌아오면 캐시 히트로 비용 절약.

## 4. 마일스톤 구성 (합의)

| 마일스톤 | 영역 | 큰 목표 | 포함 항목 |
|---------|------|---------|----------|
| **M1: 피드 검색·태그 정합** | 서버 | 올바른 기사가 올바른 태그로 들어온다 | A1, A2, A3 |
| **M2: 텍스트·LLM 출력 정제** | 서버 | 본문·요약·인사이트가 깨지지 않고 일관된다 | B1, C1, C3 |
| **M3: 데이터 모델 + 재작성 정합** | 서버 | occupation·rewrite·오답 데이터가 정확히 저장·표시된다 | D1, C2-bug, D2 |
| **M4: 클라이언트 표시·회귀** | iOS | 앱·웹 표시 일관성 + 실기기 회귀 복원 | E1, F1, F2 |

> **E2E 주의**: 각 마일스톤은 워크플로우 기본 사항으로 step-8에서 E2E 시나리오까지 통과한 뒤 done 처리 (`memory: feedback_e2e_within_workflow`).
>
> **개발 순서**: 서버 마일스톤(M1~M3) 확정 후 클라이언트(M4) 진행. iOS 회귀(F1, F2)는 서버 변경과 무관하지만 표시 변경(E1)은 서버 응답 의존이라 M4에 묶어 한 사이클로 처리 (`memory: feedback_dev_order`).

### 폐기 / 미흡수

- 시드 "소스 다양성 제한" — 실사용에서 안 아픔
- DEBT-MVP15-03 (`effective_max` 동적 감지) — 우선순위 낮음
- DEBT-MVP15-05 (`notification_service` task leak) — 우선순위 낮음

## 6. 비용 정책 주의

`memory: project_api_cost_policy` — 비용 증가 금지 원칙.

- **M1 검색 정밀화**: 쿼리 보강 정도 → 영향 낮음
