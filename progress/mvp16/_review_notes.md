## 2. C2 처리 방향 (합의)

**(3) 직업별 누적 저장 — 직업별 시점이 따로 살아있는 구조**

### 이유

- "여러 시점으로 본다"가 사용자 동기와 정합 (`memory: user_app_motivation`)
- 본인 사용 + Groq 저렴 → 비용 부담 작음
- 데이터 모델 변경 작음: rewrite 키에 `occupation` 컬럼 추가

### 스코프 포함

- 캐시 키 변경: `(user_id, article_url) → (user_id, article_url, occupation)`
- 직업 바꿨을 때 시점이 없으면 새로 생성, 있으면 즉시 표시
- **다중 시점 UX 포함** — 시점 칩 또는 펼침 UI (시안은 워크플로우에서 결정)

### 의미 변화

설정의 "직업"은 **기본/대표 시점** 의미로 약화. 다른 시점은 기사 상세에서 즉석 추가/전환 가능한 구조로 진화.

## 3. 마일스톤 구성 (합의)

| 마일스톤 | 영역 | 큰 목표 | 포함 항목 |
|---------|------|---------|----------|
| **M1: 검색·표시 정밀도** | 서버 | 올바른 기사를, 깨지지 않은 텍스트로 | A1, A2, A3, B1 |
| **M2: 재작성·요약·데이터 모델** | 서버 위주 | 여러 시점, 일관된 언어, 정확한 데이터 | C1, C2(누적+UX), C3, D1, D2 |
| **M3: 클라이언트 반영 + 회귀 수정** | 웹·iOS | 앱·웹 동작 일관성 | E1, F1, F2 |

> **E2E 주의**: 각 마일스톤은 워크플로우 기본 사항으로 step-8에서 E2E 시나리오까지 통과한 뒤 done 처리. M3가 따로 E2E 항목을 보유하지 않음 (`memory: feedback_e2e_within_workflow`).
>
> **태그 합산 정합성**은 서버 측 문제(A3)이므로 M1에서 처리. 클라이언트는 자연스럽게 따라옴.

### 폐기 / 미흡수

- 시드 "소스 다양성 제한" — 실사용에서 안 아픔, 다음 MVP 후보

## 4. 비용 정책 주의

`memory: project_api_cost_policy` 에 따라 비용 증가 금지. 변경 사항 중 비용 영향:

- **M1 검색 정밀화**: 쿼리 보강 정도라 영향 낮음
- **M2 재작성 누적 저장**: 직업 다양화로 호출 횟수 ↑ 가능 → 본인 사용이라 통제 가능
- **M2 요약 한자 혼입 수정**: 프롬프트 변경 → 비용 영향 없음
