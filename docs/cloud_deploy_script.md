# Frank 클라우드 배포 — 발표 대본

> 총 슬라이드: 13장 | 예상 발표 시간: 15~20분

---

## Slide 1 — 타이틀

안녕하세요. 오늘은 제가 만든 Frank 앱을 클라우드에 배포한 과정을 공유드리려고 합니다.

Frank는 제가 직접 쓰려고 만든 AI 기반 뉴스 스크랩 앱인데요. 서버는 Rust로, 웹은 SvelteKit으로, iOS 앱은 SwiftUI로 만든 3개 플랫폼 프로젝트입니다.

오늘 발표는 이 앱을 클라우드에 올리면서 겪은 리서치, 코드 작업, 트러블슈팅까지 전 과정을 담고 있습니다.

---

## Slide 2 — 문제

개발 자체는 완료된 상태였는데, 막상 일상에서 앱을 쓰려고 하면 하나의 근본적인 문제가 있었습니다.

서버가 제 MacBook 위에서만 돌아가고 있었어요. 즉 Mac이 꺼지면 서버도 꺼지고, 앱도 먹통이 됩니다.

외출 중에 앱을 열면 연결이 안 되고, 자려고 Mac을 끄면 그 순간부터 앱이 작동하지 않는 거죠. 개발자가 본인이 만든 앱을 본인도 제대로 못 쓰는 상황이었습니다.

오른쪽에 보시면 오늘 실제로 콘솔에 찍힌 에러입니다. `http://macbook-pro.local:8080`으로 요청이 가고 있고, "The request timed out." 이라고 나옵니다. Mac이 꺼져 있으니까요.

그래서 이번에 클라우드 배포를 결정했습니다.

---

## Slide 3 — 플랫폼 리서치

클라우드에 올리려면 가장 먼저 어떤 플랫폼을 쓸지 정해야 했습니다.

조건은 단순했어요. 월 비용 $0, 신용카드 불필요. 개인 프로젝트니까 비용이 갑자기 나가면 안 됩니다.

그래서 주요 무료 클라우드 플랫폼을 전부 검토했는데요.

**Oracle Cloud**는 이전에 ARM 서버를 받으려고 19번을 시도했는데 계속 "용량 부족"으로 실패했습니다.

**Koyeb**은 원래 괜찮은 선택지였는데, 올해 2월에 Mistral AI에 인수되면서 신규 무료 가입이 막혔어요.

**Google Cloud Run**은 카드를 필수로 요구하고, 잘못하면 과금이 나올 수 있어서 제외했습니다.

**Fly.io**는 2024년에 신규 가입자 대상 무료 티어를 종료했습니다. 기존 사용자는 레거시 플랜이 유지되고 있지만, 새로 가입해서 무료로 쓸 수는 없습니다.

결국 **Render**와 **Vercel**, 이 두 곳으로 확정했습니다. 둘 다 카드 없이 가입되고, 무료 한도 초과 시 과금이 아니라 서비스 중단 방식이라 안전합니다.

## Slide 4 — 아키텍처 Before / After

기존 구조와 배포 후 구조를 비교해 보겠습니다.

**Before**: iPhone이든 브라우저든 모두 집 Mac에 붙어 있어야 했습니다. Mac이 단일 장애점이었던 거죠.

**After**: iPhone과 브라우저는 이제 Render에 올라간 API 서버로 요청합니다. 웹은 Vercel에서 서빙되고요. 거기에 UptimeRobot이 5분마다 서버에 신호를 보내서 슬립되지 않게 유지합니다.

Mac은 이제 코드를 업데이트할 때만 필요합니다. 평소엔 꺼도 앱이 잘 동작합니다.

---

## Slide 5 — 코드 작업: health 엔드포인트

배포에 앞서 서버 코드를 하나 수정했습니다.

기존 `/health` 엔드포인트는 서버가 살아있는지만 확인하고 DB에는 아무것도 하지 않았어요. 그런데 Supabase는 7일 동안 아무 쿼리가 없으면 DB가 자동으로 정지됩니다.

UptimeRobot이 5분마다 `/health`를 호출하는데, DB 쿼리가 없으면 Supabase 입장에서는 아무도 안 쓰는 것처럼 보이는 거죠.

그래서 `/health`가 호출될 때마다 DB에 `SELECT 1`, 아주 가벼운 쿼리를 날리도록 수정했습니다. 이렇게 하면 UptimeRobot 핑 한 번으로 Render 슬립 방지와 Supabase 유지를 동시에 처리할 수 있습니다.

---

## Slide 6 — Render 배포

이제 실제 배포 과정입니다.

Render에 가입하고 GitHub을 연동한 다음, New Web Service를 만들었습니다. Runtime을 Docker로 선택하면 기존 `server/Dockerfile`을 그대로 사용합니다. 서버 코드를 전혀 건드리지 않아도 됩니다.

환경변수는 대시보드에서 입력했습니다. DB URL, Supabase 키, 각종 API 키들을 여기에 넣으면 코드에 하드코딩할 필요가 없습니다.

배포가 완료되면 URL이 발급됩니다. `curl`로 `/health`를 호출해보니 0.87초에 200 OK가 돌아왔습니다.

오른쪽에 무료 티어 스펙을 정리했는데요. 주목할 점은 한도 초과 시 과금이 아니라 서비스가 중단된다는 겁니다. 카드가 없으면 과금 자체가 불가능하고요.

---

## Slide 7 — Vercel 배포 + CORS

웹은 Vercel에 배포했습니다.

코드 변경은 딱 한 줄입니다. `svelte.config.js`에서 `adapter-node`를 `adapter-vercel`로 바꾸는 게 전부입니다. npm 패키지 하나 설치하고, import 한 줄 바꾸면 됩니다.

그런데 배포 직후에 문제가 생겼습니다. 웹에서 API 서버로 요청할 때 브라우저가 CORS 에러로 막아버렸어요.

CORS는 브라우저 보안 정책인데, 다른 도메인으로 요청할 때 서버가 명시적으로 허용해줘야 합니다. Vercel 도메인이 `frank-green.vercel.app`인데, Render 서버가 이 도메인을 모르는 상태였던 거죠.

해결은 간단했습니다. Render 환경변수에 `ALLOWED_ORIGINS`를 추가하고 Vercel 도메인을 값으로 넣은 다음 재배포. 그러면 서버가 해당 도메인에서 오는 요청을 허용합니다.

---

## Slide 8 — UptimeRobot

Render 무료 티어는 15분 동안 요청이 없으면 서버가 자동으로 슬립됩니다. 슬립 상태에서 요청이 오면 깨어나는 데 30~50초가 걸려요. 앱을 처음 켤 때 한참 기다려야 하는 상황이 생기는 거죠.

UptimeRobot은 이걸 방지합니다. 5분마다 서버에 신호를 보내서 항상 깨어있게 유지하는 무료 모니터링 서비스입니다.

설정은 간단합니다. Monitor URL에 `/health` 주소를 넣고, 간격을 5분으로 설정하면 끝입니다. 그러면 서버가 슬립될 겨를 없이 계속 유지되고, 앞서 말씀드린 것처럼 Supabase DB도 함께 유지됩니다.

부가적으로 서버가 다운됐을 때 이메일 알림도 자동으로 옵니다.

---

## Slide 9 — iOS 트러블슈팅

가장 고생한 부분입니다.

iOS 앱은 서버 URL을 `Secrets.plist` 파일에서 읽도록 돼 있었습니다. 그래서 거기서 URL을 Render로 바꾸고 빌드해서 실기기에 올렸는데, 앱이 여전히 `macbook-pro.local:8080`으로 요청하고 있었어요.

뭔가 이상해서 Xcode 콘솔 로그를 확인했더니, 슬라이드 오른쪽에 보이는 것처럼 명확하게 old MacBook URL로 요청이 가고 있었습니다.

원인을 찾아보니, iOS 프로젝트에 `Config.xcconfig`라는 파일이 있었는데 여기에도 `SERVER_URL`이 정의돼 있었습니다. 그리고 이 파일이 `Info.plist`에 주입되는 구조라, `Secrets.plist`보다 우선순위가 높았던 거예요.

정리하면 우선순위는 xcconfig → Info.plist → Secrets.plist 순서입니다. `Secrets.plist`만 바꾸면 아무 효과가 없는 거였죠.

`Config.xcconfig`에서 URL을 수정하고 나서야 정상 동작했습니다. 이런 우선순위 구조는 미리 파악하고 있어야 헤매지 않습니다.

---

## Slide 10 — 자동 재배포 파이프라인

앞으로 기능을 추가하거나 버그를 수정할 때 배포 방법을 설명드리겠습니다.

코드를 수정하고 GitHub main 브랜치에 push하면 끝입니다. Render와 Vercel이 GitHub Webhook을 통해 자동으로 감지하고, 각자 새 버전을 배포합니다. 별도로 배포 명령을 실행할 필요가 없습니다.

iOS 앱만 예외입니다. iPhone에 설치된 앱은 App Store를 거치지 않고 Xcode에서 직접 빌드해서 설치하는 방식이라, 새 기능이 생기면 Mac에서 한 번 빌드해서 설치해야 합니다. 하지만 서버와 웹은 push 한 번으로 자동 반영됩니다.

## Slide 11 — 검증 결과

실제로 다 잘 되는지 검증했습니다.

왼쪽 체크리스트를 보시면, iOS 실기기 피드 로드, 웹 브라우저 로그인과 피드, Mac을 덮은 상태(Sleep)에서 앱 동작, Playwright E2E 자동화 테스트, UptimeRobot 모니터 활성화, 자동 재배포 파이프라인 모두 확인했습니다.

오른쪽 수치를 보시면 서버 응답 시간은 약 0.9초, 싱가포르 리전 기준입니다. 그리고 월 비용은 $0입니다.

이제 실제로 어떤 상황이 가능해졌는지 정리하면요.

출근길 지하철에서 Mac 없이 iPhone으로 피드 읽고 퀴즈 풀 수 있습니다. 주말에 카페에 MacBook을 안 들고 가도 앱을 쓸 수 있습니다. 일주일 만에 앱을 열어도 UptimeRobot이 계속 서버를 유지했기 때문에 바로 피드가 뜹니다.

한 줄로 요약하면, 만든 앱을 드디어 일상에서 쓸 수 있게 됐습니다.
