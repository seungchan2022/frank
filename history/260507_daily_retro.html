⚖️ 핵심 의사결정

결정 1 — B안(PostToolUse 훅) 선택, A안과 병행

상황 step-2~8 SKILL들이 active_step.txt를 갱신하지 않음. "SKILL.md에 지시 추가"(A안) vs "훅 자동화"(B안) 중 결정.
선택지 A안: 지시 추가 (단순, 즉시) / B안: PostToolUse 훅 (Claude 의존 제거) / C안: A안만
결정 B안 근본 + A안 백업 병행
왜 step-9에 이미 갱신 지시가 있었는데 실행이 안 됐다. 같은 방식의 반복은 같은 실패다. 훅은 Claude 의존 없이 PostToolUse 이벤트에서 tool_input.skill을 파싱해 강제 갱신한다.
규칙을 문서에 추가하는 것과 기계가 강제하는 것은 신뢰성이 완전히 다르다.

결정 2 — DEBT-HOOK-03을 Phase 2로 분리

상황 Phase 1 구현 중 "/next 자동 흐름"도 같이 처리하고 싶었다.
선택지 (a) Phase 1에 포함 / (b) Phase 2로 분리, 선행 조건 명시
결정 (b) Phase 2 분리
왜 "step 완료 시그널 정의 모호" 리스크가 해소되지 않았다. Phase 1 실전 검증 후 착수 조건 명시. Phase 1이 틀어지면 Phase 2 전체가 흔들린다.
"할 수 있다"와 "지금 해야 한다"는 다르다.

결정 3 — M3 레이어 위반 그 자리에서 수정

상황 M3 step-7 리뷰에서 infra → services 의존 위반 발견.
선택지 (a) 부채 등록 후 다음 MVP에서 처리 / (b) 그 마일스톤 안에서 즉시 수정
결정 (b) 즉시 수정 — 포트 분리로 레이어 의존 제거
왜 feedback_architecture_violation_fix 원칙. 지금 작은 불편 vs 나중에 큰 리팩토링. 지금 고치는 게 훨씬 저렴하다.

결정 4 — Phase 2 착수 조건을 구체적으로 명시

상황 "Phase 2 가능"이라는 문구만 있으면 기준이 모호해서 일찍 착수할 유혹이 생긴다.
결정 "Phase 1 완료 후 실제 워크플로우 실행으로 step 추적 정확성 검증 후 착수"를 debts.md에 명문화
검증 없는 Phase 2는 "훅이 잘 작동하고 있다는 가정" 위에 복잡한 로직을 얹는 것이다.

📊 A안 vs B안 비교

항목 A안 (SKILL.md 지시) B안 (PostToolUse 훅)
신뢰성 낮음 (step-9에서 이미 실패) 높음 (Claude 의존 없음)
구현 복잡도 낮음 (텍스트 추가) 중간 (스크립트 + JSON 파싱)
필터 필요 없음 필요 (step-N 패턴만)
채택 ✅ 백업 역할 ✅ 근본 해결책

✨ 인사이트 & 피드백

같은 문제가 두 번이면 기계로 막는다.
문서·SKILL.md·CLAUDE.md에 규칙을 추가하는 것과 hook·deny·pre-commit으로 강제하는 것은 신뢰성이 완전히 다르다. "지시를 더 명확하게 쓰면 되지 않나?"가 첫 반응이었는데, step-9 케이스가 그 전략의 실패를 이미 증명했다.

진단 → 문서화 → 픽스 순서는 실제로 효과가 있다.
F1에서 "아마 ATS 문제겠지"로 추측했다면 전혀 다른 곳을 건드렸을 것이다. 진단 보고서를 써가면서 원인 후보를 좁혔기 때문에 실제 원인(API base URL 분기)까지 도달할 수 있었다.

레이어 위반은 그 자리에서 고친다.
"다음 MVP에서"라는 유혹이 항상 있다. 하지만 지금 작은 불편이 나중의 큰 리팩토링보다 훨씬 싸다.

📚 배운 것

PostToolUse 훅 stdin JSON 구조. tool_name, tool_input.skill 필드가 직접 넘어온다. jq -r '.tool_name'으로 파싱 가능하고 grep -qE '^step-[1-9]$' 필터로 특정 Skill만 골라낼 수 있다. CLAUDE_PROJECT_DIR로 레포 루트를 안전하게 참조한다.

Rust Option<Option<String>> serde 처리. JSON "키 없음(변경 안 함)"과 "키=null(삭제)"을 구분하려면 #[serde(default)] + 커스텀 deserializer 조합이 필요하다. serde_with 크레이트 없이 직접 구현 가능하다.

포트 경계를 지키면서 cascade 처리하는 방법. 단일 DB 메서드로 두 테이블을 건드리면 포트 경계 위반. 대신 핸들러에서 두 포트를 순서대로 호출(best-effort)하는 방식이 포트 분리를 지키면서 idempotent 연산을 처리하는 실용적 타협이다.

💬 느낀 점

MVP16이 끝났다. "오류·회귀 수정 사이클"이라는 정체성으로 시작했는데, 막상 끝내고 나니 단순히 버그 고치는 것 이상이었다. 내가 만든 걸 내가 쓰면서 "이게 내 생각과 맞는가?"를 확인하는 시간이 이 프로젝트에서 처음 있었다.

훅 시스템 Phase 1은 하루 만에 설계·구현·검증까지 마쳤다. 뿌듯했다. 더 중요한 건, Phase 2 설계 리스크를 명확히 인식하고 "지금은 아니다"를 결정한 것이다. 할 수 있다고 해서 지금 해야 하는 건 아니라는 걸, 이번에 조금 더 실감했다.
