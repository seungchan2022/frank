## 핵심 결정 3개

### 1. Tavily가 다시 됐는데, 그냥 쓸 수 없었다

크레딧 소진으로 Exa 기반으로 개발해왔다가, 오늘 Tavily가 갱신됐다.
그냥 쓰면 될 줄 알았는데 피드 검색 쿼리가 문제였다.
한국어 태그명("모바일 개발", "인공지능")을 그대로 Tavily에 던지면 관련 없는 결과가 섞인다.
Tavily는 영어 쿼리에 최적화된 엔진이기 때문이다.

그래서 `tag_search_keyword()` 함수를 신설해서 한국어 태그명 → 영어 검색 키워드로 매핑하는 레이어를 추가했다.
검색엔진을 바꾸는 게 단순히 API 키 교체가 아니라 쿼리 설계 자체가 달라지는 일이라는 걸 직접 확인한 날이다.

> 검색엔진은 특성이 다 다르다. 호환된다고 생각했는데 쿼리 레벨에서 맞춰줘야 했다.

---

### 2. 재작성 결과를 스크랩에 저장한 건 "당연한" 결정이었다

요약 기능은 이미 스크랩 시 함께 저장되고 있었다.
재작성 기능을 만들면서 따로 고민하지 않았다 — 요약이 저장되면 재작성도 당연히 저장돼야 한다.

사용자가 기사를 재작성해서 스크랩했다면, 나중에 스크랩함을 열었을 때 원문이 아니라 재작성된 버전을 보고 싶은 게 당연한 흐름이기 때문이다.
이건 UX 일관성의 문제였고, 결정이라기보다 확인에 가까웠다.

> 기능 추가 전에 "같은 맥락의 다른 기능은 어떻게 돼 있나"를 먼저 보는 습관이 자연스럽게 기준이 됐다.

---

### 3. /study 스킬 — 첫 사이클을 만드는 게 이렇게 오래 걸릴 줄 몰랐다

로그인 플로우를 학습했는데, 생각보다 시간이 훨씬 걸렸다.
이유가 두 가지였다.

하나는 이전에 절반쯤 만들어두고 끝내지 못한 상태에서 다시 시작했기 때문이다.
완성되지 않은 걸 이어받아서 마무리하는 게, 처음부터 만드는 것보다 오히려 더 어렵다.

다른 하나는 개념 검증이 생각보다 까다로웠다는 것이다.
"정리가 됐다" 싶은데 다시 확인해보면 틀린 개념이 섞여 있었다.
내 프로젝트 코드에 맞는 정확한 흐름과 개념인지를 확인하는 과정이 반복됐다.

한 번 사이클을 제대로 만들어두면 이후엔 그 흐름대로 자연스럽게 진행될 것이라는 기대로 시간을 쏟았다.
아직 그게 맞는 접근인지 결론은 없다.

> 처음 만드는 사이클은 항상 예상보다 오래 걸린다. 그리고 "알고 있는 것"과 "정확히 설명할 수 있는 것"은 다르다.

## 오늘의 패턴

- 검색엔진 교체는 API 교체가 아니라 쿼리 설계 교체다 — Tavily 복귀가 그걸 가르쳤다
- 기존 기능의 동작 방식이 새 기능의 설계 기준이 된다 — 요약이 재작성 저장의 근거였다
- 완성되지 않은 작업을 이어받는 게 처음부터 만드는 것보다 오래 걸릴 수 있다
- "정리됐다"와 "맞다"는 다른 말이다 — 개념 검증은 한 번으로 끝나지 않는다
