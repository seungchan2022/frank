오늘 뭘 했나

클라우드 배포 하나에 온종일 집중했다. 방향이 여러 번 바뀌었지만 결국 다 됐다.

오전: 배포 플랫폼 재탐색. Oracle Free Tier 시도가 19번 실패한 상태였다. 춘천 리전 ARM 재고 부족이 근본 원인이었고, 재시도로 해결될 문제가 아니었다. Koyeb를 알게 됐는데 신규 가입이 막혀 역시 불가. 직접 탐색해서 찾은 게 Render(API) + Vercel(웹) 조합이었다.

오후: 실제 배포. SvelteKit adapter 1줄 교체, Rust 바이너리 Render 배포, UptimeRobot 5분 핑 + health DB ping 설정까지 마쳤다.

저녁: 보안 검토 + 발표 자료. 배포 전 보안 검토를 요청해서 E2E 테스트 평문 크리덴셜을 발견하고 즉시 환경변수로 교체했다. 학교 발표용 슬라이드 13장도 완성했다.

핵심 의사결정

결정 1 — Render + Vercel 조합 확정

WHY Oracle은 외부 재고 문제, Koyeb는 신규 불가. 무료 + 즉시 사용 가능한 조합이 필요했다.

HOW Render: Rust 바이너리 직접 배포, 무료 750시간/월. Vercel: SvelteKit official adapter 지원, 1줄 교체.

인사이트 Oracle 19번 시도는 당시 최선의 방법이었다. 틀린 판단이 아니었다. "내가 통제할 수 없는 장벽"이라는 판단이 섰을 때 전환한 것도 맞는 결정이었다.

결정 2 — UptimeRobot + health DB ping으로 슬립 방지

WHY Render free tier는 15분 비활성 시 슬립. 콜드 스타트 30~60초 발생.

HOW UptimeRobot 무료 플랜 5분 간격 핑. /health 엔드포인트에 DB ping 추가 → API 슬립 방지 + Supabase keep-alive 동시 해결.

인사이트 심층 리서치로 Render의 약점을 미리 파악하고 보완책을 함께 붙였다. Oracle 성공 시나리오보다 더 견고한 구성이 됐을 수 있다.

결정 3 — E2E 크리덴셜 즉시 환경변수 교체

WHY 배포 전 보안 검토 타이밍에 E2E 테스트 파일에서 test@test.com 평문 발견.

HOW E2E_TEST_EMAIL, E2E_TEST_PASSWORD 환경변수로 즉시 교체. 커밋 98f2eec.

인사이트 "배포 전에 한번 훑자"는 작은 습관이 실제 문제를 잡았다. 규칙으로 강제하기보다 이 습관 자체를 유지하는 것이 맞다.

결정 4 — Oracle을 포기한 시점

WHY 실패 패턴이 "내 설정 오류"가 아니라 "리전 재고 부족"이라는 외부 요인이었다.

인사이트 내가 통제할 수 없는 요인이 문제라면, 재시도 횟수를 늘리는 것은 해결책이 아니다. "포기"가 아니라 "전환"이라는 구분.

인사이트

"혼자 돌아간다"는 것의 체감. 맥을 끄고 앱이 실행되는 걸 확인한 순간이 오늘의 핵심이었다. 빌드 성공, 테스트 통과, 커밋 올라가는 것과는 완전히 다른 종류의 완성감이다.
보완책을 함께 붙이면 단순 교체보다 더 나은 결과가 나온다. Render의 약점(슬립)을 조사하고 대응책(UptimeRobot)을 같이 설계했다. 플랫폼을 바꾼 게 아니라 더 견고한 시스템을 만든 것에 가깝다.
배포 중 보안 검토 타이밍은 습관으로 남겨야 한다. "올리기 전에 한번 훑자"는 사소한 결정이었는데, 그 타이밍에 실제 문제가 잡혔다.

배운 것

Render + Vercel 배포 패턴

Render: render.yaml 또는 대시보드에서 빌드 커맨드 설정. Vercel: adapter-vercel 설치 후 svelte.config.js 1줄 교체. 두 플랫폼 모두 GitHub push 시 자동 재배포.

UptimeRobot 슬립 방지

무료 플랜 5분 간격 HTTP 모니터링. Render free tier 슬립 기준(15분)보다 짧게 핑하면 슬립 방지. /health 에 DB ping 추가 시 Supabase idle connection 해제도 방지.

SvelteKit adapter 구조

배포 환경에 따라 adapter를 교체하는 것이 SvelteKit 설계 의도. adapter-node → adapter-vercel은 npm install 1번 + config 1줄. 서버 로직 변경 없음.

느낀 점

클라우드 배포를 오래 끌어왔다. Oracle이 안 됐을 때 "이게 정말 안 되는 건지, 내가 놓치는 게 있는 건지"를 구분하기가 어려웠다. 오늘 Render + Vercel로 배포가 됐을 때, Oracle이 재고 문제였다는 판단이 맞았다는 걸 확인했다.

서비스가 "살아있다"는 건 맥이 꺼져 있어도 앱이 돌아간다는 것이다.
