## 오늘 뭘 했나

클라우드 배포 하나에 온종일 집중했다. 방향이 여러 번 바뀌었지만 결국 다 됐다.

**오전: 배포 계획 재수립.** Oracle Free Tier 시도가 19번 실패한 상태였다. 춘천 리전 ARM 재고 부족이 근본 원인이었고, 계속 기다려도 해결될 문제가 아니었다. 오늘은 "다른 방법"을 찾는 것부터 시작했다. Koyeb를 알게 됐는데 신규 가입이 막혀 있어서 역시 불가. 직접 탐색해서 찾은 게 Render(API 서버) + Vercel(웹) 조합이었다.

**오후: 실제 배포 작업.** SvelteKit adapter를 `adapter-node`에서 `adapter-vercel`로 교체하는 것은 `svelte.config.js` 1줄 변경이었다. Render는 Docker 없이 Rust 바이너리 직접 빌드로 배포했다. 배포 자체보다 Render free tier의 15분 슬립 문제를 어떻게 처리할지가 핵심이었는데 — UptimeRobot으로 5분마다 헬스체크 핑을 날리는 방식으로 해결했다. 이 과정에서 `GET /health` 엔드포인트에 DB ping을 추가해서 Supabase connection keep-alive도 같이 잡았다.

**저녁: 보안 검토 + 발표 자료.** Vercel adapter 커밋 직후 보안 검토를 요청했고, E2E 테스트에 하드코딩된 `test@test.com / Test1234!` 평문이 발견됐다. 즉시 환경변수로 교체했다. 이미 git 히스토리에는 남아있었지만 앞으로의 커밋에는 올라가지 않게 처리했다. 이후에는 학교 발표용 슬라이드 13장을 만들었다. 배포 구조 전체를 시각화하고 팩트체크까지 포함했다.

## 핵심 의사결정과 그 이유

### 결정 1 — Render + Vercel 조합으로 확정

- **상황**: Oracle 19회 실패, Koyeb 신규 불가. 무료 + 즉시 사용 가능한 플랫폼이 필요했다.
- **선택지들**:
  - Oracle: ARM 재고 부족으로 계속 실패 중, 언제 해소될지 모름
  - Koyeb: 신규 계정 생성 불가 (서비스 정책 변경)
  - Render + Vercel: Render는 API 서버 무료 호스팅, Vercel은 SvelteKit 공식 지원
  - Railway: 유료 플랜 필요
- **결정**: Render(API) + Vercel(웹).
- **왜**: Render는 Rust 바이너리 직접 배포 지원, 무료 750시간/월. Vercel은 SvelteKit official adapter 존재 — 1줄 코드 변경으로 호환. 두 플랫폼 모두 GitHub 연동 자동 배포 지원. 가장 적은 설정으로 가장 빠르게 배포 가능한 조합.
- **인사이트**: Oracle을 19번 시도한 건 당시 "무료이면서 문제가 없는 최선의 방법"이었기 때문이다. 틀린 판단이 아니었다. 하지만 19번이라는 데이터가 쌓인 시점에서 "이건 재고 문제라 나의 재시도로 해결이 안 된다"고 판단하고 다른 옵션을 탐색한 것도 맞는 결정이었다.

---

### 결정 2 — UptimeRobot + health DB ping으로 슬립 방지

- **상황**: Render free tier는 15분 비활성 시 슬립. 콜드 스타트 시 첫 요청이 30~60초 걸린다.
- **선택지들**:
  - (a) 그냥 두기 — 콜드 스타트 수용
  - (b) UptimeRobot 5분 핑 — 슬립 방지
  - (c) 유료 플랜 업그레이드 — 슬립 없음
- **결정**: (b). UptimeRobot 무료 플랜으로 5분마다 `/health` 핑.
- **왜**: 개인 사용 앱에서 유료 플랜은 과하다. 단순 핑 방식으로 충분히 슬립을 방지할 수 있다. `/health` 엔드포인트에 DB ping을 추가한 건 일석이조 — API 슬립 방지 + Supabase connection 유지.
- **인사이트**: 심층 리서치를 통해 Render의 알려진 문제점(슬립)을 미리 파악하고 보완책을 함께 붙였다. 단순히 플랫폼을 교체한 게 아니라, 그 플랫폼의 약점을 알고 처리한 구성이라 더 견고하다.

---

### 결정 3 — E2E 크리덴셜 즉시 환경변수 교체

- **상황**: 배포 작업 중 보안 검토를 요청. E2E 테스트 파일에서 `test@test.com / Test1234!` 평문이 발견됐다.
- **결정**: 즉시 환경변수(`E2E_TEST_EMAIL`, `E2E_TEST_PASSWORD`)로 교체.
- **왜**: 배포 전 올라가면 안 되는 내용이 있는지 확인하려는 타이밍이 맞았다. 보안 분석에서 F-02로 식별된 항목이었고, "나중에 처리"가 아니라 발견 즉시 처리하는 것이 맞다. 이미 히스토리에 남아있는 부분은 어쩔 수 없지만, 앞으로의 커밋은 깨끗하게 유지된다.

---

### 결정 4 — Oracle을 포기한 시점

- **상황**: Oracle을 계속 시도하는 것이 합리적인지 판단이 필요했다.
- **결정**: 19번 실패 후 다른 플랫폼 탐색으로 전환.
- **왜**: 실패 패턴이 "내 설정 오류"가 아니라 "리전 재고 부족"이라는 외부 요인이었다. 내가 통제할 수 없는 요인이 문제라면, 내 재시도 횟수를 늘리는 것은 해결책이 아니다.
- **인사이트**: 언제 포기할지를 결정하는 기준이 중요하다. "틀린 방법이어서 포기"가 아니라 "내가 통제할 수 없는 장벽이어서 전환"이라는 구분.

```

  → ARM 재고 부족, 외부 요인
  ↓

  ↓
Render(API) + Vercel(웹) 선택

  ↓
맥 끄고 앱 실행 확인 → 배포 완료
```

## 인사이트 & 피드백

**"혼자 돌아간다"는 것의 체감.** 맥을 끄고 앱이 실행되는 걸 확인한 순간이 오늘의 핵심이었다. 빌드가 성공하고, 테스트가 통과하고, 커밋이 올라가도 — "로컬 없이 인터넷에서 혼자 돌아가는 것"은 완전히 다른 종류의 완성감이다. 배포를 처음 완성한 날이기도 하다.

**보완책을 함께 붙이면 단순 교체보다 더 나은 결과가 나온다.** Oracle이 됐어도 슬립 방지 구성이나 health ping이 들어갔을지 모른다. Render로 전환하면서 그 플랫폼의 약점을 조사하고 대응책을 같이 설계했기 때문에, 결과적으로 Oracle 성공 시나리오보다 더 견고한 시스템이 됐을 수 있다.

**배포 중 보안 검토 타이밍은 습관으로 남겨야 한다.** "올리기 전에 한번 훑자"는 사소한 결정이었는데, 그 타이밍에 실제 문제(E2E 평문 크리덴셜)가 잡혔다. 규칙으로 강제하기보다 "배포 전 보안 검토" 습관을 자연스럽게 이어가는 게 맞을 것 같다.

## 배운 것

**Render + Vercel 배포 구성.** Render는 `render.yaml` 또는 대시보드에서 빌드 커맨드 설정, Vercel은 SvelteKit `adapter-vercel` 패키지 설치 후 `svelte.config.js` 1줄 교체로 끝. 두 플랫폼 모두 GitHub push 시 자동 재배포 지원.

**UptimeRobot 슬립 방지 패턴.** 무료 플랜 5분 간격 HTTP 모니터링. Render free tier 슬립 기준(15분)보다 짧은 간격으로 핑하면 슬립이 발생하지 않는다. `/health` 엔드포인트에 DB 연결 확인을 추가하면 Supabase idle connection 해제도 함께 방지.

**SvelteKit adapter 구조.** 배포 환경에 따라 adapter를 교체하는 것이 SvelteKit의 설계 의도. `adapter-node` → `adapter-vercel`은 `npm install` 1번 + config 1줄로 전환 가능. 서버 로직은 변경 없음.

## 느낀 점

클라우드 배포를 오래 끌어왔다. Oracle이 안 됐을 때 "이게 정말 안 되는 건지, 내가 놓치는 게 있는 건지"를 구분하기가 어려웠다. 오늘 Render + Vercel로 10분 안에 배포가 됐을 때, Oracle이 재고 문제였다는 게 맞는 판단이었다는 걸 확인했다.

배포 완성은 단순히 코드를 올리는 게 아니라는 걸 오늘 다시 느꼈다. 맥이 꺼져 있어도 앱이 돌아간다는 것 — 그게 서비스가 "살아있다"는 의미라는 걸.
